# Правила App Store, Google Play, RuStore и AppGallery: трекинг, рекламные идентификаторы и раскрытие данных SDK

> **Это правило магазина приложений, не законодательство РФ.** Нарушение ведёт к отклонению или снятию приложения из стора, а не к ответственности по российскому праву. Для iOS- и Android-приложений с аналитикой, рекламными и атрибуционными SDK эти правила — отдельный слой требований поверх 152-ФЗ. Тексты сторов охраняются авторским правом, поэтому ниже — пересказ по состоянию страниц на 2026-09-29 (Apple, Google) и 2026-10-01 (Apple 5.1.2(i), RuStore, Huawei AppGallery). Даты редакций на страницах Apple о приватности, Google и RuStore не указаны, кроме журнала изменений страницы Data safety (последняя запись — 05.12.2023); у App Store Review Guidelines — «Last Updated: June 8, 2026»; у разделов AppGallery указаны версии и даты.

## Суть требования

**Apple (iOS, iPadOS, tvOS):**

- **Раскрытие в App Store Connect.** При отправке нового приложения или обновления разработчик указывает практики обработки данных. Из них формируются «Privacy Nutrition Labels» на странице приложения. Сторонний код (реклама, аналитика) раскрывается тоже: какие данные собирает, как использует, ведёт ли трекинг.
- **App Tracking Transparency (ATT).** Начиная с iOS/iPadOS/tvOS 14.5, для трекинга пользователя или доступа к рекламному идентификатору (IDFA) нужно разрешение через ATT. Без разрешения IDFA возвращается нулями.
  - Трекинг — связывание данных приложения с данными других компаний для таргетированной рекламы или измерения рекламы, а также передача данных брокерам данных.
  - Пример из правил: SDK, который объединяет данные разных приложений, — это трекинг, даже если сам разработчик так его не использует.
  - Исключения: связывание только на устройстве без передачи; передача брокеру только для антифрода и безопасности; передача кредитному бюро для кредитных целей.
- **Системный запрос** должен содержать purpose string с объяснением цели. Показать его можно в любой момент, но IDFA доступен только после разрешения.
- **Fingerprinting запрещён.** Приложения с такими SDK могут быть отклонены.
- **IDFV** можно использовать для аналитики между приложениями одного поставщика без ATT, но не для трекинга.
- **Ответственность за SDK.** Разработчик отвечает за весь код приложения, включая сторонние SDK: «Developers are responsible for all code included in their apps» (Apple, User Privacy and Data Use).
- **Privacy manifests и подписи.** Манифест описывает практики обработки данных стороннего кода в едином формате, Xcode сводит манифесты в отчёт. Для SDK из списка Apple манифест обязателен при отправке нового приложения или обновления, которое добавляет такой SDK. Если SDK из списка подключён как бинарная зависимость, нужна также подпись SDK (требование подписи привязано к SDK из списка, а не ко всем бинарным зависимостям). Требование охватывает любые версии SDK из списка и SDK, которые их переупаковывают. На 2026-09-29 в списке 85 позиций, в том числе модули Firebase, Facebook SDK, GoogleSignIn, Flutter, Capacitor, Cordova, UnityFramework; AppMetrica, MyTracker, Adjust и AppsFlyer в нём нет. Список меняется.
- **5.1.2(i) — передача ПДн третьим лицам, в том числе стороннему ИИ** (App Store Review Guidelines, «Last Updated: June 8, 2026», снято 2026-10-01). Нужно ясно раскрывать, куда передаются персональные данные третьим лицам, «including with third-party AI», и получать явное разрешение пользователя до передачи.

**Google Play (Android):**

- **Data safety.** Форму в Play Console заполняют все разработчики опубликованных приложений, включая приложения на закрытых, открытых и production-треках тестирования и приложения, которые данные не собирают. Приложения, активные только на внутреннем тестовом треке (internal testing), от заполнения освобождены (с 24.10.2022), как и системные сервисы и private-приложения. Нужна также ссылка на политику конфиденциальности.
- **Данные SDK и webview.** В декларацию включаются данные, которые собирают и передают сторонние библиотеки и SDK, в том числе при передаче с устройства напрямую третьему лицу, а также данные из webview, если приложение контролирует его код.
- **Ответственность.** За полноту и точность декларации отвечает разработчик. При расхождении с реальным поведением приложения возможны меры принуждения.
- **Прочее.** «Эфемерную» обработку тоже декларируют, но профилирование и реклама эфемерными не считаются. Псевдонимные данные, которые можно разумно связать с пользователем, раскрываются.
- **Advertising ID.** Сбрасываемый и удаляемый пользователем идентификатор; после удаления возвращается строка нулей.
  - Приложения с target API 33 (Android 13) и выше объявляют разрешение `com.google.android.gms.permission.AD_ID` в манифесте. Некоторые SDK добавляют его через слияние манифестов.
  - Для рекламы используется только Advertising ID (если доступен), а не другие идентификаторы устройства.
  - Для нерекламных задач (аналитика, антифрод) рекомендован App Set ID.
  - Для нерекламных целей постоянные идентификаторы допустимы при наличии политики конфиденциальности и соблюдении применимого законодательства о приватности.
  - Если Advertising ID на устройстве нет, страница допускает постоянный или собственный идентификатор при тех же условиях (политика конфиденциальности, Developer Distribution Agreement, законы о приватности).

**RuStore (Android) — «Гайд по требованиям к приложениям»** (живая страница 2026-10-01, пересказ):

- **5.1 Политика конфиденциальности** (если собираются ПДн): ссылка в карточке и внутри приложения; на русском языке; категории данных, цели, сроки хранения, порядок удаления, контакты ответственного лица.
- **5.2.** Запрещено: сбор без оснований, использование не по заявленным целям, скрытое профилирование, первичный сбор и хранение ПДн граждан РФ с нарушением локализации. Обязательно: согласия, в том числе отдельные, где они требуются; раскрытие в карточке категорий данных и целей; соблюдение требований к оператору ПДн. По запросу RuStore разработчик даёт документы о соблюдении законодательства о ПДн.
- **5.3 и 6.3 Разрешения.** Только нужные для функций; обоснование каждого; работа при отказе от необязательных. Уровни: запрещённые (версия отклоняется), чувствительные (обоснование в форме загрузки), безопасные, устаревшие. Данные из разрешений нельзя продавать и передавать третьим лицам; согласие — активным действием. При нарушениях возможна блокировка приложения и аккаунта.
- **9.4** — задекларировать в консоли все рекламные SDK, сети, медиаторы и сервисы передачи данных в рекламных целях. **9.8** — уведомлять пользователя о рекламе; раскрывать в политике конфиденциальности рекламные SDK, категории данных и цели; не передавать ПДн рекламным сервисам без предусмотренных законодательством оснований.
- **2.14** — среди признаков, по которым версия может быть отклонена, — «аномальное количество трекеров… без надлежащего информирования».
- **9.7** — в приложениях 0+ и 6+ поведенческая реклама запрещена; подробнее — [Правила сторов: дети и возрастной рейтинг](pravila-storov-deti-i-vozrastnoy-reyting.md).

**RuStore — «Соглашение для разработчиков»** (договор площадки, снят 2026-10-01, пересказ):

- **4.5** — разработчик выступает «самостоятельным и независимым от Компании оператором персональных данных» пользователей своих продуктов. Он поручает RuStore обработку платёжных данных пользователей (дата, время, сумма, чек, ARN, 3DS, наименование продукта, подтверждения передачи товара или оказания услуги и ознакомления с условиями автосписаний) в целях исполнения Соглашения, в том числе для споров об оплатах (4.5.1–4.5.2). Способы обработки — от сбора до уничтожения (4.5.3), срок — до окончания действия Соглашения (4.5.4). RuStore обязуется соблюдать конфиденциальность, требования ч. 5 ст. 18 и ст. 18.1 152-ФЗ, по запросу разработчика (в том числе до обработки) предоставлять документы о принятых мерах, обеспечивать безопасность ПДн (4.5.5); в RuStore «реализованы требования к защите» (4.5.6); RuStore уведомит разработчика о неправомерной или случайной передаче поручённых данных, повлёкшей нарушение прав пользователей (4.5.7).
- **4.4** — в продуктах и (или) вместе с ними размещается ссылка на политику конфиденциальности. **4.9** — продукт не передаёт данные пользователя «без явного на то согласия».

**Huawei AppGallery — Review Guidelines V28, раздел 7 «Приватность пользователя»** (V2 от 2026-01-07, пересказ):

- Раздел ссылается на GDPR, законы КНР, Гонконга, Сингапура «и иные применимые»; требования AppGallery дополняют закон. Россия не упомянута.
- **7.1–7.3** — легко находимая ссылка на политику конфиденциальности в приложении и в AppGallery Connect; цели, способы и объём обработки, в том числе третьими лицами и SDK; как реализовать права; канал обратной связи.
- **7.5–7.8** — согласие до сбора, когда его требует закон или оно выбрано основанием; простой отзыв согласия; **независимая опция отключения персонализированной рекламы и маркетинга**; явное согласие для чувствительных данных.
- **7.9–7.19** — минимизация; без скрытого сбора; HTTPS; раскрытие получателей; **запрет продажи ПДн**; 7.15 — запрет использовать чувствительные данные (журналы звонков, SMS, биометрию, здоровье, геолокацию) для улучшения сервиса, рекламы, маркетинга и иных неосновных функций; 7.16 — нельзя отказывать в услуге из-за отказа в согласии; 7.17 — геолокация не только для рекламы и аналитики.
- **7.20–7.24 OAID** — только для рекламы и аналитики; не связывать с персональными данными и постоянными идентификаторами без явного согласия; проверять настройку «отключить персонализированную рекламу»; не связывать новый OAID со старым.

## Кому и когда применяется

- **Кому.** Любой разработчик, публикующий приложение в App Store, Google Play, RuStore или AppGallery, независимо от страны и правовой формы. Для B2B-приложений правила те же.
- **Триггеры:**
  - Apple ATT — трекинг в смысле Apple или доступ к IDFA;
  - privacy manifest — наличие SDK из списка Apple;
  - Google Data safety — любое опубликованное приложение в Google Play, кроме приложений только на внутреннем тестовом треке;
  - разрешение AD_ID — target API 33+ и использование Advertising ID;
  - Apple 5.1.2(i) — передача ПДн третьим лицам, в том числе стороннему ИИ;
  - RuStore 5.1–5.2 — сбор ПДн; 9.4 и 9.8 — рекламные SDK и сети; 6.3 — чувствительные разрешения;
  - AppGallery, раздел 7 — обработка ПДн; 7.20–7.24 — использование OAID.
- **Когда.** При каждой отправке нового приложения или обновления. Даты в raw: ATT — с iOS 14.5; освобождение внутреннего тестирования от Data safety — с 24.10.2022; строка нулей вместо удалённого Advertising ID на всех устройствах с Google Play — с 01.04.2022. Дату вступления требований к privacy manifests страница Apple не указывает (механизм представлен на WWDC23). RuStore — гайд и соглашение сняты 2026-10-01, даты редакций не указаны; соглашение меняется со дня, следующего за публикацией новой редакции (п. 11.1). AppGallery, раздел 7 — V2 от 2026-01-07.
- **Применимость к боту:** нет — это правила магазинов приложений (App Store, Google Play, RuStore, AppGallery); бот и Mini App внутри мессенджера в магазин не подаются, правила платформы мессенджера — отдельный слой.

## Исключения

- Apple: исключения из понятия трекинга (на устройстве, антифрод, кредитные цели), IDFV внутри приложений одного поставщика.
- Google: эфемерная обработка может не отображаться (но декларируется); приложения только на внутреннем тестовом треке, системные сервисы и private-приложения форму Data safety не заполняют. Сбором не считаются обработка только на устройстве и данные со сквозным шифрованием. Передачей не считаются передача сервис-провайдеру, для правовых целей, по действию пользователя или после заметного раскрытия и согласия, а также анонимизированных данных.
- RuStore и AppGallery проверены 2026-10-01; исключений из своих требований к раскрытию данных они в пересказе не называют. Другие сторы не проверялись.

## Смежные требования законодательства РФ

- **Идентификаторы как ПДн.** IDFA, IDFV, Advertising ID, App Set ID и данные SDK могут быть ПДн — см. [cookies и идентификаторы как ПДн](cookies-i-identifikatory-kak-pdn.md).
- **Согласие.** Разрешение ATT — правило стора, а не основание обработки по 152-ФЗ. Вывод: у системного запроса нет конкретности, предметности и отдельного оформления по ч. 1 ст. 9 152-ФЗ, поэтому согласием по ст. 9 он сам по себе не является. Требует отдельной оценки. Со стороны Apple собственные экраны согласия для соблюдения местного законодательства допускаются, но ответ пользователя на ATT должен соблюдаться в любом случае (FAQ страницы User Privacy and Data Use; см. исправленный пересказ Apple в Sources). Там же: на юридическое согласие, уже полученное через свой экран или CMP, можно сослаться в purpose string ATT, а тем, кто отказался от всех соответствующих согласий, запрос ATT показывать не следует. См. [основание и согласие для аналитики](soglasie-na-analitiku-i-cookies.md).
- **Политика.** Privacy labels и Data safety не заменяют политику по ч. 2 ст. 18.1 152-ФЗ, но должны ей соответствовать. В деле 2КСОЮ № 16-9987/2022 объём обработки суд установил по политике конфиденциальности самого оператора. Публичные декларации о данных могут стать доказательством. См. [политика обработки ПДн](politika-obrabotki-pdn.md).
- **SDK-поставщики, локализация, трансграничная передача** — [поставщики аналитики и SDK](postavshchiki-analitiki-i-sdk.md).
- **Роль оператора и поручение.** По соглашению RuStore (п. 4.5) разработчик — самостоятельный оператор ПДн, а RuStore обрабатывает платёжные данные по его поручению. По живому тексту (сверено 2026-10-01) поручение содержит элементы, которые перечисляет ч. 3 ст. 6 152-ФЗ: перечень данных (4.5.2), действия с ними (4.5.3), цели (4.5.1), конфиденциальность и требования ч. 5 ст. 18 и ст. 18.1, документы по запросу оператора, в том числе до обработки, обеспечение безопасности (4.5.5), уведомление о неправомерной или случайной передаче (4.5.7). Требования к защите по ст. 19 названы только общей фразой «реализованы требования к защите» (4.5.6), без перечня; достаточно ли этого, чтобы они были «указаны» в поручении, — трактовка, открытый вопрос. Договорная квалификация сама по себе роль не определяет. См. [Поручение обработки ПДн](poruchenie-obrabotki-pdn.md) и [Владелец продукта как оператор ПДн](operator-pdn-po-statusu-vladelca.md).
- **Локализация.** RuStore 5.2 запрещает первичный сбор и хранение ПДн граждан РФ с нарушением локализации; правовой слой — [Локализация ПДн](lokalizaciya-pdn.md).
- **Отказ в услуге из-за отказа в согласии** (AppGallery 7.16) по направлению совпадает с законодательным запретом (вывод) — [Запрет отказа потребителю без ПДн](zapret-otkaza-potrebitelyu-bez-pdn.md).
- **Передача ПДн стороннему ИИ** (Apple 5.1.2(i)). По 152-ФЗ это может быть поручение или передача третьему лицу, а при иностранном сервисе — ещё и трансграничная передача (вывод). См. [Трансграничная передача ПДн](transgranichnaya-peredacha-pdn.md); правила сторов об ИИ — [Правила сторов: генеративный ИИ](pravila-storov-generativnyy-ii.md).

## Позиции органов и практика

- Правоприменение — модерация и меры сторов. Российской судебной практики о правилах сторов не исследовалось.
- В практике по 152-ФЗ (дело Ookla) публичные документы оператора использованы как источник фактов об объёме обработки.

## Техническое проявление в продукте

- **iOS:**
  - вызов запроса ATT до доступа к IDFA и до инициализации рекламных и атрибуционных SDK в режиме трекинга;
  - purpose string (ключ `NSUserTrackingUsageDescription` в Info.plist — инженерная практика, имя ключа в raw не сверено);
  - privacy manifest приложения и SDK (файл `PrivacyInfo.xcprivacy` — инженерная практика, имя файла в raw не сверено); проверка отчёта Xcode;
  - отказ от SDK с fingerprinting.
- **Android:**
  - проверка итогового (merged) манифеста на `com.google.android.gms.permission.AD_ID`;
  - использование App Set ID вместо Advertising ID для аналитики;
  - заполнение Data safety по реестру SDK, включая webview.
- **RuStore:**
  - ссылка на политику конфиденциальности на русском — в карточке и внутри приложения;
  - раскрытие категорий данных и целей в карточке; декларация рекламных SDK, сетей и медиаторов в консоли (9.4), согласованная с политикой (9.8);
  - обоснование чувствительных разрешений в форме загрузки; работа приложения при отказе от необязательных разрешений.
- **AppGallery:**
  - независимый переключатель отключения персонализированной рекламы и маркетинга;
  - OAID не связывается с ПДн и постоянными идентификаторами без явного согласия; учитывается настройка «отключить персонализированную рекламу».
- **Передача данных в сторонний ИИ (Apple 5.1.2(i)):** экран раскрытия и явного разрешения до первой передачи ПДн ИИ-сервису (инженерная практика).
- **Общее:** единый реестр SDK и данных как источник для privacy labels, Data safety, деклараций RuStore и политики по 152-ФЗ (инженерная практика).

## Что нельзя проверить по репозиторию

- Что заявлено в App Store Connect и Play Console (privacy labels, Data safety), в RuStore Консоли (рекламные SDK, разрешения, категории данных) и AppGallery Connect (ссылка на политику, описание разрешений).
- Какая редакция соглашения RuStore действовала на дату присоединения: редакции меняются публикацией.
- Настройки SDK на стороне поставщиков (атрибуция, обмен данными с рекламными сетями).
- Состав текущего списка SDK Apple, для которых нужен манифест.
- Были ли у приложения отклонения или предупреждения от сторов.

## Пробелы и спорные места

- Страницы Apple и страница Google об Advertising ID не содержат дат редакций; у страницы Data safety есть только журнал изменений (последняя запись 05.12.2023). Основные политики (App Review Guidelines, Developer Program Policy) не прочитаны.
- Страница Data safety противоречит сама себе в вопросе эфемерной обработки: по разделу о сборе её включают в ответы формы, по FAQ — можно не включать.
- Относится ли допуск запасного идентификатора «на устройствах без Advertising ID» к случаю, когда пользователь удалил ID и приложение получает нули, страница не уточняет.
- Правила RuStore прочитаны 2026-10-01, но дата редакции гайда не указана. Список «Типы разрешений» RuStore не проверен; соглашение прочитано частично (разделы 6–8 и 10 — по ключевым словам). Критериев «аномального количества трекеров» (2.14) RuStore не даёт.
- Поручение в соглашении RuStore содержит элементы ч. 3 ст. 6 152-ФЗ, но требования к защите по ст. 19 названы общей фразой без перечня (п. 4.5.6). Достаточно ли этого, не установлено. Прежний вывод «по пересказу установить нельзя» снят: raw пересказал п. 4.5 не полностью, недостающее — в дополняющем raw.
- AppGallery: соглашение разработчика Huawei не проверено; Россия в разделе 7 не упомянута.
- Apple 5.1.2(i): что считается «third-party AI», в пересказе не определено.
- Является ли согласие через ATT или системный запрос согласием по ст. 9 152-ФЗ — вывод «нет» без практики.
